# ADR-005: Confirm API에 Pessimistic Lock을 적용한 이유

- Status: Accepted
- Context: 동일 Meeting에 최종 확정 요청이 동시에 들어오면 상태·History·Notification의 중복/불일치가 발생할 수 있다.
- Decision: Confirm은 Meeting row를 Pessimistic Lock으로 조회하고 VOTING 불변식과 Candidate 소속을 확인한 뒤 한 트랜잭션에서 확정한다.
- Alternatives: Lock 없음, Optimistic Lock, DB 제약만 사용.
- Consequences: 확정 요청이 직렬화되지만 Confirm은 저빈도이고 정합성 우선 도메인이다.
- Verification: 동시 Confirm 50건에서 성공 1건, MeetingHistory 1건, 확정값 일관성 비교 실험.
