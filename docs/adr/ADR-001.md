# ADR-001: JWT + Redis Auth Session 선택 이유

- Status: Proposed — A 담당자가 보안 실험 후 세부안 확정
- Context: SPA와 Spring API를 분리하고, 로그아웃·Refresh Rotation·재사용 탐지·Rate Limit·1회용 초대 토큰을 서버에서 제어해야 한다.
- Decision: Access Token은 JWT를 사용하고 인증 세션/Refresh lifecycle/Rate Limit/Invite Token 상태는 Redis에서 관리하는 방향을 기본안으로 둔다. Refresh Token의 브라우저 저장 위치와 Rotation 세부 구조는 A가 `localStorage vs HttpOnly Cookie`, blacklist vs current token id 등을 비교한 뒤 본 ADR을 갱신한다. 백본의 `csrf.disable()`은 임시값이며 HttpOnly Cookie 선택 시 CSRF 방어까지 함께 재설계한다.
- Alternatives: 완전 Stateless JWT, Refresh Token DB 저장, 서버 HTTP Session.
- Consequences: Redis 장애가 인증 갱신에 영향을 줄 수 있으나 TTL/원자 연산을 활용할 수 있고 강제 로그아웃·재사용 탐지가 가능하다.
- Verification: 이전 Refresh Token 재사용 401, 세션 폐기, Rate Limit TTL 복구, Invite Token 1회 사용 동시 요청 테스트. JWT PR에서 `AuthenticationEntryPoint`/`AccessDeniedHandler`도 공통 ErrorResponse 계약(401/403)에 맞춘다.
